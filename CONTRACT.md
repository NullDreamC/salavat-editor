# Local application contract

Python FastAPI + SQLite backend in `server/`, React + Vite TypeScript frontend in `web/`. Backend serves built UI at 127.0.0.1:8000. Vite proxies /api to :8000. All UI Russian, sparse, calm white/teal, no promotional copy. Auth cookie, same origin; no keys in browser.

## Extended editorial workflow (2026-11-14)

The Telegram/report continuation adds `server.telegram_intents` (private free-text requests, ambiguity choices, reply-bound clarifications and nonce/version-bound schedule confirmations) and `server.reports`. Attachments, image directives and existing post reply bindings retain their existing pipeline. Unknown free text asks whether it is post material or a task; no model call is needed for routing. Date/time mutations require a concrete confirmation and invalidate approval.

`TaskCreate` and routine schemas accept `notify_telegram` (default false). Explicit web opt-in requires a valid current Telegram binding/bot; existing records are migrated with opt-in disabled. The creator's recipient and bot identity are pinned and rechecked on delivery; routine execution actor and notification creator are separate. Terminal results/questions/failures have a bounded preview and cabinet link. Scheduled failures create one persisted failed task per due slot with an audit entry; no paid request is made for invalid prerequisites.

`GET /companies/{cid}/reports` returns safe history/schedules/eligible recipients. `GET /reports/preview?days=1|7` prepares current measured data; `POST /reports {days}` retains the author's first snapshot for that local period; `POST /reports/{id}/send` queues its delivery. `/reports/schedules` POST and `/{id}` PUT manage daily/weekly schedules with version checks; `/{id}/disable?version=...` disables. Company timezone governs full prior day/seven-day windows. After downtime only the latest eligible scheduled slot is generated. Reports summarize actual publication audit events, created task cohorts, current queue and latest stored Telegram metrics with observation dates. Unknown counts remain unknown. Reports use no generation API or new VK/MAX integration.

Report delivery runs independently from polling. Current role, recipient binding, exact bot token fingerprint and schedule version are checked; definite unsent transient failures retry with backoff, ambiguous outcomes stay uncertain. Schedules and notification opt-ins are created only at user request, never enabled by migration.

Lifecycle registers `knowledge`, `assistant_tasks`, `review_policy`, `social_platforms`, `analytics`, and `inbox` after database initialization. All editorial routes deny super_admin; social connection/reviewer policy metadata remains administrable by global accounts without personal profile fields.

- `/companies/{cid}/knowledge`: GET list, POST create from text/source, PATCH item, DELETE archive. `/import-url` imports bounded public HTTPS HTML/text to draft with redirect/DNS checks. Only active same-company immutable snapshots enter generation; historical citations survive edits, revoked snapshots cannot be selected for a new generation. `company_seed.seed_salavat_knowledge` is explicit and idempotent, never an automatic new-company default.
- `/tasks`: GET/POST durable conversation tasks, GET item, POST `/{id}/messages` and `/retry`. Kinds chat/strategy/topics/plan/video. Queue states queued/running/completed/needs_info/failed/interrupted. Provider claims, current membership, source evidence, active knowledge and attempt identity are checked. Factual output requires evidence; proposals are explicitly labeled. On restart running tasks become interrupted, never automatically replayed. `/plan` supports CRUD and `/{id}/post`; conversion creates an empty draft with source IDs and author, not an approved model-generated brief. `/routines` supports CRUD and `/{id}/run`; daily/weekly company-local slots, one occurrence per local day and no previous-day backlog.
- Posts expose `platform:telegram|vk|max` and `created_by`. Platform/address/media/time changes invalidate approval. Non-Telegram destination must match connection settings. Provider drafts see platform context. Long VK/MAX posts receive bounded Telegram previews with cabinet links and review controls. `/review-policy` stores assigned reviewer IDs; empty means every current admin/approver, configured inactive reviewers do not silently widen approval. `/posts/{id}/reconcile` manually records published IDs or returns a confirmed-unsent post to draft; it never sends.
- `/social/{vk|max}` GET safe metadata/PATCH encrypted-token settings; enabled with stored token is not a live connectivity certificate. Adapters support approved publication, available counters, comments and replies. Ambiguous sends stay locked. Public HTTPS upload destinations are validated. MAX self comments are marked against `/me`; anonymous MAX comments are not eligible for automatic replies.
- `/analytics` returns dated observations, coverage, formats and deterministic findings/hypotheses; `/metrics`, `/import`, `/sync` add observations with provenance. Missing counts stay unknown. ER requires complete known interactions and positive reach. Linked post/platform/external ID must agree; Telegram IDs require a channel-qualified identity.
- `/inbox` supports manual intake, social sync, draft editing/generation, approval, close, and send. Generation claims prevent duplicate paid calls for the same in-flight item. Approval binds exact reply/version, sends claim durable state and preserve uncertain outcomes. `/settings` licenses active FAQ snapshot IDs and is disabled by default. Automatic replies only use exact normalized FAQ matches from synchronized comments and current admin authorization; they do not run a model. `/monitor` independently enables 15-minute checks of at most five actually published VK/MAX posts in the last 30 days. Posts reconciled without a known publication time require manually dated metrics.

Worker cycles for Telegram, paid assistant tasks, scheduled jobs and monitored inboxes are independent per company. Scheduled VK/MAX publication does not require Telegram credentials. Telegram assistant replies bind company, bot, chat, user and request; definitely unsent transient errors have bounded retry/backoff, uncertain sends remain blocked with audit. Post authors and assigned reviewers receive relevant notifications when their membership remains active.

Explicit post-creation requests within assistant conversations create a real publication rather than a prose-only answer. The request resolves its topic from conversation context, grounds content in company sources, and invokes the existing image/logo workflow when an image is requested. Request-to-post linkage preserves completed stages for retries. Ready posts enter review, never automatic publication; Telegram delivers their actual media and version-bound controls to the authorized requester. An uncertain delivery is not silently repeated.

Membership `can_approve` defaults to false and grants editors post approval, rejection, publication, and publication reconciliation in that company only. Company admins may set it through employee create/patch; role changes clear it unless a company admin explicitly grants it with the new editor role. It does not grant company administration or inbox approval. Post actions recheck active membership and this capability in the transaction; Telegram buttons and reviewer notifications use the same eligibility. Explicit reviewer assignments still constrain approval/rejection/reconciliation. Global technical access records retain only ID, company, role, and status.

`server.tunnel_runner` supervises the previously approved localhost.run configuration, reconnects after an activity timeout and updates the exact WebApp origin. A per-directory process lock prevents duplicate supervisors; `.runtime/tunnel.stop` stops it. Windows DPAPI credentials remain tied to the original account/computer; cloud migration requires new secret provisioning.

## HTTP interface

For the exact configured WebApp host, CSRF checks and session cookie flags use the configured HTTPS origin even when localhost.run forwards plain HTTP without X-Forwarded-Proto. Unrelated Origin values and cross-site fetches remain blocked; arbitrary proxy headers cannot authorize another origin. Cookie deletion uses the same Secure/HttpOnly/SameSite settings as login.

Model discovery returns general text-model families from the live catalog. Speech/realtime/transcription, image/video, embeddings/moderation, search/research, coding and computer-use specializations are excluded; fine-tuned models are classified by their base model. This category filter does not certify every model's image or structured-output capabilities.

`server.tunnel_watch` follows the authorized localhost.run SSH log and atomically updates the active origin on domain rotation. Host validation reloads the exact origin per request; previous public hosts immediately stop being accepted. The worker updates the bot menu on its next cycle. Existing Telegram messages with old inline URLs require reopening through the current bot menu.

`GET /companies/{id}/models?provider=openai|yandex` returns a live sorted, deduplicated string array from the provider Models API. Company admin or super_admin only. Stored tenant credentials and explicitly scoped OpenAI.txt fallback only; browser never sees credentials. Yandex returns text-generation model names stripped of this folder's `gpt://` prefix. Provider/network errors become safe 502 responses, never a web-session 401. No generation or usage record is created.

The optional Telegram WebApp origin comes from `webapp.json` beside the database; only its exact hostname is allowed in addition to loopback. HTTPS cookies permit Telegram frames and remain Secure/HttpOnly. CSRF and role checks remain enforced. Unknown Telegram senders may open the login button and see their own ID only, without tenant data. The worker synchronizes bot commands/menu. `server.setup_telegram` configures a company's bot from a token file without printing its secret. Optional `network.json` configures this app's outbound HTTP proxy.

All endpoints `/api`. Errors `{detail: string}`. Cookie session, JSON unless upload. Login `POST /auth/login {email,password}` => User. `GET /auth/me` => User. `POST /auth/logout`. `GET /auth/setup` => `{required:bool}`; `POST /auth/setup {name,email,password}` creates the first super_admin and 3 companies, logs in; no company memberships or publicly known default passwords.

`POST /auth/password {current_password,new_password}` => 204, changes own password and revokes every session including current. `POST /companies/{id}/users/{user_id}/password {new_password}` => 204, company admin resets another non-global account and revokes all its sessions. Reset of a shared account requires admin membership in every company that account belongs to. Super_admin cannot reset employee passwords. Password length 10–256, hashes only, audit never includes passwords. Shared-account password applies across companies. Password operations recheck the session inside the write transaction; login rechecks the verified password hash before creating a session.

User `{id,name,email,role}` role super_admin/admin/editor/approver. User identity is returned to its own authenticated session; employee profiles are visible only to admins of that company. `GET /companies` => Company[] (all for super_admin, memberships for others), `POST /companies {name}` (super_admin only); Company `{id,name,role?,timezone,calendar_enabled,provider,model,channel_id,chat_id,bot_username,yandex_folder_id,monthly_limit,requests_limit}`. `PATCH /companies/{id}` mutable fields plus optional `openai_key,yandex_key,telegram_token` (write-only), never return secrets. `GET /companies/{id}/settings` => Company plus `openai_configured,yandex_configured,telegram_configured` booleans. Company settings are managed by company admin or super_admin.

`GET/POST /companies/{id}/users` company admin only; create `{name,email,password,role,telegram_id?}`. Existing accounts join another company by invitation, never by guessed email. `PATCH /companies/{id}/users/{user_id}` for role/telegram_id/active. Company admins cannot remove the last active company admin. `GET /companies/{id}/access` super_admin only, returns exactly `{id,company_id,role,active}` per employee. `PATCH .../access/{user_id}` accepts role/active only and revokes the affected employee's sessions. No employee names, email, Telegram IDs, content, activity or password resets are available to the global account. Super_admin is denied tenant editorial routes even if a legacy membership exists. The migration removes legacy global memberships and sessions once, preserving accounts, passwords and company data.

`POST /companies/{id}/invitations {role}` company admin or super_admin => `{id,token,role,expires_at}`. Single-use invitation valid for 7 days, only token hash stored. `GET .../invitations` => `{id,role,expires_at,status}` without recipient data; `DELETE .../invitations/{id}` revokes. Public `GET /invitations/{token}` => `{company_name,role}`; `POST .../accept {name,email,password}` creates an employee or verifies an existing employee's password and adds membership, then logs in. Issuer authority and token validity are rechecked atomically. Global accounts cannot accept employee invitations. UI uses `/#invite=token`; recipients enter their own personal information.

`GET /companies/{id}/sources` => Source[], `POST .../sources {title,text}` => Source. `POST .../uploads` multipart `file` => Source. Source `{id,title,text,kind,created_at,file_url?,mime_type?}`; kind text/image/document/video. Uploads protected, NOT arbitrary workspace files.

`GET /companies/{id}/posts` => Post[], `POST .../posts {source_ids:number[],title?,kind?}` => Post. `GET/PATCH /companies/{id}/posts/{post_id}`; patch `{title?,body?,channel_id?,scheduled_at?,template?,source_ids?,version}`. Post `{id,title,body,kind,status,version,source_ids,questions,created_at,scheduled_at,channel_id,template,card_url?,publication_url?,feedback?}`. statuses draft/needs_info/review/approved/publishing/published/rejected/failed. questions string[]. `POST .../posts/{id}/generate {version}` calls AI. `POST .../posts/{id}/answer {text,version}` adds source and regenerates. `POST .../posts/{id}/submit {version}` review, `POST .../posts/{id}/approve {version}`, `POST .../posts/{id}/reject {version,comment}`, `POST .../posts/{id}/publish {version}`. Optimistic version check, every content change increments version and invalidates approval. Publish approved exact snapshot only, atomic claim, ambiguous transport outcome no automatic retry. `POST .../posts/{id}/card {version}` renders fixed template via server.cards (root builds). template announcement/person/results; image response via authorized source endpoint. Any created card invalidates approval and increments version.

`GET/POST /companies/{id}/events` => Event[], create `{title,event_date,description?,source_id?}`; Event `{id,title,event_date,description,source_id,reminded_at?}`. `PATCH/DELETE .../events/{event_id}`. Calendar disabled rejects scheduled extraction/reminders, hides nav but manual settings preserve stored events.

`GET /companies/{id}/activity` => Audit[] `{id,action,detail,created_at}`; `GET /companies/{id}/usage` => `{requests,input_tokens,output_tokens,monthly_limit,requests_limit}` (no fabricated ruble spend).

## Integration Python interfaces (agent owns server/integrations.py)

`async generate_post(company:dict, sources:list[dict], instruction:str, credentials:dict) -> dict` => `{title,body,questions:list[str],facts:list[dict],events:list[dict],input_tokens,output_tokens}`. credentials keys openai_key/yandex_key. Read OpenAI.txt safely as fallback backend only. No offline fake generation; clear missing config error. Images from source `file_path,mime_type` only (backend supplies scoped files). questions nonempty => needs_info. Grounding source IDs required and validated. Events only exact ISO dates with source evidence.

`async telegram_call(token, method, payload=None, files=None) -> dict` unwrap result; safe errors no credentials; `async publish_telegram(token,channel_id,body,media:list[dict]) -> dict` => `{message_id,publication_url?}`. Media dict file_path/mime_type. Throw explicit exceptions, don't repeat requests on uncertain delivery. `message_is_addressed(message, bot_username, bot_id=None)->bool` parses actual Telegram mention entities; sender allowlist applied by worker separately.

## Company controls, Telegram linking and photos

`DELETE /companies/{id}` archives a company (global admin only), retains data and stops tenant access/background work. Reject during publication or when company 1 supplies active Salavat-funded companies. `funding_mode` is own/salavat/shared. Global admin assigns source and a mandatory positive `requests_limit` for pooled credentials. Company admins cannot change pooled funding/caps/credentials. `GET/PATCH /shared-api` global only; write-only OpenAI/Yandex keys and Yandex folder. Model discovery and generation resolve the assigned supplier; Telegram credentials always stay tenant-specific. Usage reservations are atomic, counted against requesting company in UTC month. Text reserves one request. Photo generation with automatic logo selection atomically reserves two requests, with separate token records. Manual logo replacement is local and uses no provider calls or quota.

`GET /companies/{id}/telegram-link` returns linked/configured booleans for the current employee. `POST` issues `{command,bot_username,expires_at,url}`; token is hashed, single-use, expires in 10 minutes, scoped to employee/company/bot. The bot accepts it in private `/start` messages and binds the authenticated sender's numeric ID. Global admins use a separate company account for editorial work.

`GET/PATCH /companies/{id}/brand` manages `light_background,dark_background,accents,theme` and reports light/dark/primary logo flags. `POST .../brand/logos/{light|dark|primary}` uploads a transparent PNG; filenames and server paths cannot be supplied by clients. Prefer the primary corporate colour on light coloured/neutral backgrounds, black on white, white on dark. Company 1 has all three bundled assets; other companies require their own (primary optional).

`POST /companies/{id}/posts/{post_id}/photo {version,mode:original|create|edit,instruction?,source_id?}` changes publication imagery and invalidates approval. Generated `photo_id/photo_url` is separate from factual `source_ids`, replaces original photos in outgoing media, and survives text regeneration. Original mode restores supplied photos. `generate_photo` creates clean artwork and automatically selects a logo via vision, returning both the clean base and branded image. The clean base is retained as private `photo_base_id`. If automatic layout fails, paid artwork is retained with `logo_pending` for manual selection; image generation is not repeated. Post fields `logo_editable`, `logo_pending`, `logo:{variant,corner,width}|null` describe logo state. Original mode/source replacement clears this state. Telegram exact starred directives select modes; ordinary hashtags do not. Media groups are assembled before processing.

`GET .../posts/{id}/logo` returns `{variants,placement}`. `POST .../posts/{id}/logo {version,variant:primary|light|dark,corner:top_left|top_right|bottom_left|bottom_right,width?:0.32..0.38}` applies the original PNG to the saved clean image (default width 0.35), never to an already branded image. Both corner edges have equal margins of 3.5% image width. Text, facts, sources and underlying image remain unchanged; a new photo/version invalidates approval. Admin/editor can change an editable post; approver can change logos during review/approved, returning it to review. Current membership, company, status and version are rechecked on save. Global admin is denied. Generated images need a selected logo before submission/approval/publication; original-photo mode is exempt. Older generated images without saved clean artwork need regeneration before logo-only editing.

Telegram `logo` opens selections; `logopick` updates colour/corner without changing the post; `logoapply` commits both choices and returns a fresh preview. Callback data includes the post version; stale buttons cannot change newer content. Manual logo replacement uses no paid model calls. Ready Telegram drafts automatically submit to review; reviewers see approve/reject/edit plus a separate logo button. Editor-only accounts cannot approve or reject. `edit` creates a sender/chat/company/version-bound reply prompt: editors/admins call `Service.revise`, preserving photo/base/logo while updating text with grounded sources; approvers return a comment to the editor via rejection. Stale/replayed replies cannot change a newer version. Successful delivery marks the recipient's review notification delivered, avoiding duplicate previews.

Design guidance retained for the image composition and editor: evaluate the entire mark and lettering footprint, including lamps, highlights and windows. White/dark recommendations apply to uniform backgrounds; primary is preferred on mixed backgrounds where white loses contrast on highlights and black on shadows. AI selects the first colour and corner; the editor can override them using the manual controls.
